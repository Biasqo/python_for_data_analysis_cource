## Конкурентность vs Параллелизм, GIL

### Идея
Разобраться в двух понятиях и показать на опыте, что **потоки в CPython не ускоряют CPU-bound код** из-за GIL.

- **Конкурентность**: несколько задач *делают прогресс по очереди* (переключаются), необязательно одновременно.
- **Параллелизм**: несколько задач *реально выполняются в один момент* на разных ядрах.

### Как работает
1. `cpu_bound(n)` считает `sum(i*i for i in range(n))`. Это чистые вычисления, без ожидания.
2. **Последовательно:** 4 вызова по `N // 4` подряд в одном потоке.
3. **Через threading:** 4 потока, каждый считает свой кусок, и главный поток ждёт их через `join()`.
4. Выводятся оба времени.
5. Отдельная ячейка показывает `os.cpu_count()`: сколько ядер *могло бы* работать параллельно.

### Ключевые моменты
- Объём работы одинаковый, поэтому честно сравниваем только способ выполнения.
- **GIL** (Global Interpreter Lock) пропускает байткод Python только одному потоку за раз. Потоки по очереди получают GIL, и вычисления не ускоряются.
- Время `threading` будет **примерно таким же, как последовательное**, а часто даже чуть хуже из-за накладных расходов на переключение потоков.
- Вывод: для CPU-bound задач нужны **процессы** (`multiprocessing`), для I/O-bound подходят **потоки или asyncio**.

## Будущее GIL: PEP 703

### Идея
Показать, что GIL можно отключить: в новых версиях Python появилась экспериментальная **free-threaded** сборка.

### Как работает
1. `getattr(sys, "_is_gil_enabled", None)` проверяет, существует ли функция. Она есть только в Python 3.13+.
2. Если функция есть, она возвращает `True/False`: включён GIL или нет.
3. Если функции нет, значит, сборка не поддерживает free-threaded режим.
4. Печатается версия интерпретатора (`sys.version`).

### Ключевые моменты
- **PEP 703** предлагает сделать GIL опциональным. Отдельная сборка (обычно `python3.13t`) работает без него.
- В такой сборке пример с `threading` из предыдущего блока уже даст реальное ускорение.
- Стандартная сборка по-прежнему работает с GIL, поэтому на обычном интерпретаторе скорее всего будет `GIL включён: True`.
- Режим пока имеет ограничения: часть сторонних библиотек не готова к работе без GIL, а в однопоточном коде бывают небольшие потери производительности.
- Паттерн `getattr(..., None)` это безопасная проверка наличия возможности на разных версиях Python.

## Базовый синтаксис Threading

### Идея
Показать, что потоки хорошо работают с **I/O-bound** задачами (ожидание сети, диска): ожидания перекрываются.

### Как работает
1. `download(name, delay)` печатает начало, «ждёт» `delay` секунд через `time.sleep` и печатает конец. Это имитация загрузки файла.
2. Создаётся 5 потоков (`threading.Thread(target=..., args=...)`). На этом этапе они **ещё не запущены**, при печати списка видно состояние `initial`.
3. `t.start()` запускает все потоки, `t.join()` ждёт их завершения.
4. Общее время ≈ **1 секунда**, а не 5.

### Ключевые моменты
- `time.sleep` (как и сетевые/файловые операции) **освобождает GIL**, пока поток ждёт. Поэтому другие потоки работают в это время.
- Сообщения «Начало» идут пачкой, потом «Завершена», и порядок завершения может отличаться от порядка запуска.
- Два цикла нужны именно такие: в первом запускаем *все* потоки, и только потом во втором ждём. Если делать `start()` и `join()` в одном цикле, потоки выполнятся последовательно.
- Для CPU-bound задач эта схема не помогает (см. первый блок).

## Coroutine, Task, Future и базовый синтаксис

### Идея
Знакомство с `asyncio`: **кооперативная многозадачность в одном потоке**. Задачи сами «отдают управление» в точках `await`.

### Как работает: пример с загрузкой
1. `async def download_async(...)` создаёт **корутину**. При вызове функция не выполняется, а возвращает объект корутины.
2. `await asyncio.sleep(delay)` приостанавливает корутину и возвращает управление **event loop**, который в это время запускает другие.
3. `asyncio.gather(...)` оборачивает корутины в задачи, запускает их конкурентно и ждёт все.
4. Итог ≈ **1 секунда** вместо 5, как и в варианте с потоками, но **без потоков**, в одном потоке.

### Три понятия
| Понятие | Что это |
|---|---|
| **Coroutine** | Результат вызова `async def`: «заготовка» кода, которую можно приостанавливать |
| **Task** | Обёртка над корутиной, поставленная в расписание event loop (`asyncio.create_task`) |
| **Future** | «Обещание результата»: объект, значение которого появится позже. Task является Future |

### Как работает: `bad` vs `good`
- `bad()` использует **блокирующий** `time.sleep` внутри `async def`. Пока он «спит», event loop **заморожен**, и остальные задачи не могут работать. Итог ≈ **1,5 сек** (3 × 0,5).
- `good()` использует `await asyncio.sleep`, который отдаёт управление. Итог ≈ **0,5 сек**.

### Ключевые моменты
- Слово `async` само по себе ничего не распараллеливает. Выигрыш даёт только **неблокирующее ожидание через `await`**.
- Главное правило asyncio: **никогда не блокируйте event loop** (`time.sleep`, синхронные HTTP-запросы, тяжёлые вычисления).
- Для CPU-bound внутри asyncio используют `run_in_executor` / отдельные процессы.

### Нюанс (неточный комментарий в коде)
В выводе для `bad()` написано «перекрылись, выполнились последовательно». Это противоречие: они **не перекрылись**, а выполнились последовательно. Лучше: `<- не перекрылись, выполнились последовательно`.

## Ограничение конкурентности: Semaphore

### Идея
Запускаем 100 задач одновременно, но к «ресурсу» (например, API с лимитом) пускаем не более 10 одновременно.

### Как работает
1. `Semaphore(10)` это счётчик из 10 «разрешений».
2. `async with semaphore:` забирает разрешение при входе и возвращает при выходе. Если разрешений нет, корутина **ждёт**.
3. `fetch_all` создаёт 100 корутин и запускает их через `gather`. Все стартуют сразу, но внутрь защищённого блока попадают только 10.
4. Внутри блока `sleep(0.2)` имитирует запрос и формируется «цена».
5. Время ≈ 100 / 10 × 0,2 = **около 2 секунд** (вместо 20 при последовательном запуске и ~0,2 без ограничения).

### Ключевые моменты
- Семафор нужен, чтобы не «заспамить» сервер и не упереться в rate limit или лимит соединений.
- В логе видно, как счётчик убывает до 0 и затем возвращается к 10, когда задачи освобождают места.
- `gather` сохраняет порядок результатов, как и порядок тикеров.
- `semaphore._value` — приватный атрибут, используется здесь **только для демонстрации**. В реальном коде им пользоваться не стоит.
- `hash(ticker)` для строк рандомизирован при каждом запуске Python, поэтому «цены» от запуска к запуску разные.

## gather vs as_completed vs TaskGroup

### Идея
Сравнить способы ожидания нескольких задач. В этом блоке показаны два из трёх, `TaskGroup` разбирается в следующем.

### Как работает
Три воркера с задержками 0,3 / 0,1 / 0,2 сек возвращают свои номера 1, 2, 3.
- **`gather`** вернёт результаты **в порядке передачи**: `[1, 2, 3]`.
- **`as_completed`** отдаёт результаты **по мере готовности**: `2 3 1` (сначала самый быстрый).

### Ключевые моменты
| | `gather` | `as_completed` |
|---|---|---|
| Порядок результатов | как при запуске | как при завершении |
| Когда получаем результат | когда готовы **все** | как только готов **очередной** |
| Применение | нужен полный набор по порядку | хочется обрабатывать результаты сразу (прогресс, стриминг) |

- Порядок у `gather` важен, когда результат нужно сопоставить с входом (например, список тикеров).
- `as_completed` полезен, когда задачи сильно различаются по времени и ждать самую медленную не хочется.

## Структурная конкурентность

### Идея
**Structured concurrency**: время жизни задач ограничено блоком кода. Выйти из блока можно, только когда все задачи внутри завершены. Для этого в Python 3.11+ есть `asyncio.TaskGroup`.

### Пример 1: успешный сценарий
1. `async with asyncio.TaskGroup() as tg:` открывает группу.
2. `tg.create_task(...)` запускает задачи внутри группы.
3. При выходе из блока группа **автоматически ждёт все задачи**.
4. После блока результаты берутся через `t1.result()`, `t2.result()`.

(Строка `results = []` перед группой лишняя, значение сразу перезаписывается.)

### Пример 2: ошибка в одной из задач
1. `failing_worker` через 0,1 сек бросает `ValueError`.
2. `long_worker` собирается спать 5 секунд.
3. `TaskGroup`, получив ошибку, **отменяет всех соседей**: в `long_worker` приходит `CancelledError` (корутина печатает сообщение и пробрасывает его дальше через `raise`).
4. Группа выбрасывает **`ExceptionGroup`**, в котором лежат все ошибки.

Весь блок занимает ~0,1 сек, а не 5.

### Пример 3: то же через `gather(..., return_exceptions=True)`
- `gather` **не отменяет** соседей при ошибке.
- `long_worker` дорабатывает все 5 секунд и вернёт строку `"не должно сюда дойти"` (в данном случае она всё-таки возвращается).
- В списке результатов будет и объект исключения, и обычное значение: `[ValueError(...), 'не должно сюда дойти']`.

### Сравнение
| | `TaskGroup` | `gather(return_exceptions=True)` |
|---|---|---|
| При ошибке одной задачи | остальные **отменяются** | остальные **продолжают** |
| Исключения | собираются в `ExceptionGroup` | возвращаются как элементы списка |
| «Висящие» задачи после блока | невозможны | возможны |

### Ключевые моменты
- `CancelledError` всегда нужно пробрасывать (`raise`) после очистки, иначе отмена не сработает.
- `TaskGroup` безопаснее: нет «забытых» задач и утечек.

### Нюанс (ошибка в коде)
```python
except ValueError as eg:
    print(len(eg.exceptions))
```
`TaskGroup` выбрасывает **`ExceptionGroup`**, а не `ValueError`, поэтому такой `except` ничего не поймает, и ячейка упадёт с трейсбеком. (Атрибут `.exceptions` есть только у группы.) Правильно использовать `except*`:
```python
except* ValueError as eg:
    print(f"Поймано исключений в группе: {len(eg.exceptions)} -> {eg.exceptions[0]}")
```
или `except ExceptionGroup as eg:`.

## Асинхронные контекстные менеджеры

### Идея
Обычный `with` вызывает `__enter__`/`__exit__`. Если открытие или закрытие ресурса требует ожидания (сеть, БД), нужны **`async with`** и методы **`__aenter__`/`__aexit__`**, внутри которых можно делать `await`.

### Как работает
1. `async with AsyncDatabaseConnection() as conn:` вызывает `__aenter__`: печатается «Открываем соединение...», асинхронная пауза (имитация подключения), возвращается `self`.
2. Внутри блока выполняется `await conn.query(...)`.
3. При выходе автоматически вызывается `__aexit__`: «Закрываем соединение...» (тоже с `await`).
4. Порядок вывода: открытие → результат запроса → закрытие.

### Ключевые моменты
- Закрытие гарантируется, даже если внутри блока случилось исключение. `__aexit__` получает информацию об исключении в аргументах `exc_type, exc_val, exc_tb`.
- Здесь `__aexit__` ничего не возвращает (то есть `None`), значит, исключения **не подавляются**.
- Типичное применение: пулы соединений и сессии БД/HTTP (`aiohttp.ClientSession`, `asyncpg`), блокировки (`async with lock`), семафоры (как в блоке выше).

## Асинхронные генераторы

### Идея
Генератор, который может **ждать между выдачами значений**. Подходит для потоков данных: котировки, сообщения, чтение по частям.

### Как работает
1. `async def` + `yield` создаёт **асинхронный генератор**.
2. На каждой из 5 итераций функция «ждёт» 0,2 сек (имитация прихода новой цены) и выдаёт словарь `{"ticker": ..., "price": 100 + i}`.
3. `async for price in stream_prices("AAPL"):` получает значения **по мере поступления**.
4. Вывод: 5 словарей с ценами 100…104, примерно по одному каждые 0,2 сек.

### Ключевые моменты
- Обычный `for` с таким генератором не работает: нужен `async for`, который сам делает `await` на каждом шаге.
- Данные обрабатываются лениво, потоком, без накопления всего списка в памяти.
- Пока генератор «спит», event loop выполняет другие задачи.
- Как и `await`, `async for` можно использовать только внутри `async def` (или в ячейке Jupyter).
