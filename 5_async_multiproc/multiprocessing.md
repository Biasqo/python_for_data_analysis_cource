## base_multiprocessing.py

### Идея
Самый простой пример: запускаем **один дочерний процесс**, который выполняет тяжёлое вычисление, а родитель ждёт его завершения.

### Как работает
1. `Process(target=worker, args=(N,))` создаёт объект процесса, но пока ничего не запускает.
2. `p.start()` запускает новый процесс ОС. Он выполняет `worker(N)`: считает сумму квадратов чисел от 0 до 100 000 000 и печатает её.
3. `p.join()` блокирует родителя, пока дочерний процесс не завершится.
4. После этого родитель печатает «Дочерний процесс завершён».

### Ключевые моменты
- **У каждого процесса своя память и свой интерпретатор** (и свой GIL). Дочерний процесс не может просто «вернуть» значение через `return`: здесь результат просто печатается внутри `worker`.
- **`if __name__ == '__main__':` обязателен.** На Windows и macOS (метод запуска `spawn`) дочерний процесс заново импортирует модуль. Без защиты он снова запустил бы создание процессов (бесконечная рекурсия или ошибка).
- Без `join()` родитель мог бы завершиться раньше ребёнка, а «Дочерний процесс завершён» напечаталось бы до результата.
- Пользы от параллелизма здесь нет: процесс один. Пример нужен, чтобы показать базовый жизненный цикл: `create → start → join`.

### Нюанс
`Queue` импортирован, но не используется. Это «хвост» от следующего примера.

## base_multiprocessing_2.py

### Идея
Делим одну большую задачу на части по числу ядер, считаем части параллельно, а результаты собираем через **`Queue`**.

### Как работает
1. `cores = os.cpu_count()`: узнаём число логических ядер.
2. Диапазон `[0, N)` режется на `cores` кусков по `chunk = N // cores`. **Последний** процесс берёт остаток (`end = N`), иначе при неделимости N часть чисел потерялась бы.
3. Для каждого куска создаётся `Process(target=worker, ...)`, и все они запускаются сразу.
4. Каждый `worker` считает сумму квадратов своего куска и кладёт результат в `queue`.
5. Родитель делает `join()` для всех процессов, затем забирает результаты из очереди и суммирует.

### Ключевые моменты
- **`Queue`** это потокобезопасный и процессобезопасный канал «ребёнок → родитель». Данные внутри сериализуются (pickle).
- Порядок завершения процессов и порядок результатов в очереди **не детерминирован**, но сумма от порядка не зависит.
- В выводе строки `Worker i (PID ...)` появляются в произвольном порядке, так как процессы работают одновременно. Разные PID показывают, что это действительно разные процессы.

### Нюансы (хорошо обсудить со студентами)
- `while not q.empty()` ненадёжен: документация прямо говорит, что `empty()` приблизителен. Надёжнее так:
  ```python
  total = sum(q.get() for _ in range(cores))
  ```
- Безопасный порядок обычно такой: **сначала получить данные из очереди, потом `join()`**. Если в очередь кладут большие объекты, процесс не завершится, пока их никто не прочитал, и `join()` зависнет (deadlock). Здесь результаты маленькие, поэтому всё работает.

## gil_fix.py

### Идея
Показать, что **multiprocessing обходит GIL** и даёт реальное ускорение на CPU-bound задачах.

### Как работает
1. Задача `cpu_bound(n)` считает `sum(i*i for i in range(n))`. Это чисто вычислительная работа без ввода-вывода.
2. **Последовательно:** 4 раза подряд вызываем `cpu_bound(N // 4)` в одном процессе и замеряем время.
3. **Параллельно:** `Pool(processes=4)` создаёт 4 процесса-воркера, `pool.map` раздаёт им 4 одинаковые задачи, и они выполняются одновременно.
4. Сравниваем время.

### Ключевые моменты
- **GIL** (Global Interpreter Lock) позволяет только одному потоку выполнять байткод Python в один момент времени. Поэтому `threading` не ускоряет CPU-bound код.
- У каждого процесса свой интерпретатор и свой GIL, поэтому 4 процесса реально занимают 4 ядра.
- Объём работы в обоих вариантах одинаковый (4 × 37,5 млн итераций). Отличается только способ выполнения.
- Ускорение **не будет ровно 4x**: есть накладные расходы на запуск процессов и передачу данных, а также зависимость от числа физических ядер. Если ядер меньше 4, выигрыш меньше.
- `with Pool(...)` автоматически завершает пул при выходе из блока.

### Нюанс (баг в выводе)
Обе строки подписаны «Multiprocessing». Вторая должна быть `Sequential`:
```python
print(f"Multiprocessing : {multiprocessing_time:.2f} сек")
print(f"Sequential      : {sequential_time:.2f} сек")
```

## pool_n_pool_exec.py

### Идея
Сравнить два высокоуровневых API для пула процессов: **`multiprocessing.Pool`** и **`concurrent.futures.ProcessPoolExecutor`**. Заодно показать, что между процессами можно передавать даже `DataFrame`.

### Как работает
1. `process_dataframe(seed)` генерирует 1000 случайных чисел (нормальное распределение, генератор инициализируется `seed`), нормализует их (z-score) и добавляет колонку `source` с номером seed.
2. Для `seeds = 0..7` задача запускается на пуле из 4 процессов дважды: через `Pool.map` и через `ProcessPoolExecutor.map`.
3. Результаты (списки DataFrame) склеиваются через `pd.concat`.
4. `groupby("source")["normalized"].mean()` показывает среднее по каждому источнику. Оно будет **≈ 0** (порядка 1e-16), потому что данные нормализованы.
5. `final_df.equals(final_df2)` проверяет, что оба подхода дали **идентичный** результат.

### Ключевые моменты
- **Результат совпадает**, потому что генератор случайных чисел инициализируется seed, и результат не зависит от того, какой процесс выполнил задачу.
- Оба `map` **сохраняют порядок** входных данных, даже если задачи завершаются в другом порядке.
- DataFrame возвращается из воркера через **pickle**. Это работает, но для больших объёмов данных становится дорого (см. `serialization.py`).
- Функция воркера должна быть определена на верхнем уровне модуля, чтобы её можно было сериализовать.

### Сравнение API

| | `Pool` | `ProcessPoolExecutor` |
|---|---|---|
| Модуль | `multiprocessing` | `concurrent.futures` |
| `map` возвращает | список | итератор (поэтому `list(...)`) |
| Дополнительно | `imap`, `starmap`, `apply_async` | `submit` + `Future`, `as_completed` |
| Единый интерфейс с потоками | нет | да (`ThreadPoolExecutor`) |

### Нюанс
Строка `final_df2 = pd.concat(results, ...)` выполняется дважды подряд. Второй вызов лишний.

## atomic.py

### Идея
Продемонстрировать **состояние гонки (race condition)** при работе с общей переменной и как его устраняет **`Lock`**.

### Как работает
1. `Value('i', 0)` создаёт целое число в **разделяемой памяти**, доступное всем процессам.
2. Два процесса по `N = 200 000` раз делают `counter.value += 1`. Ожидаемый результат: **400 000**.
3. **Без блокировки** итог будет **меньше** 400 000 и каждый запуск разный.
4. **С блокировкой** (`with lock:`) итог всегда ровно **400 000**.

### Почему так происходит
Операция `counter.value += 1` не атомарна, это три шага:
```
1. прочитать value        (tmp = value)
2. увеличить на 1         (tmp = tmp + 1)
3. записать обратно       (value = tmp)
```
Если два процесса прочитали одно и то же значение, оба запишут `tmp + 1`, и **одно увеличение потеряется**.

`Lock` делает так, что вся тройка шагов выполняется одним процессом, пока остальные ждут.

### Ключевые моменты
- У `Value` есть внутренний замок, но он защищает только отдельные чтения и записи, а не всю конструкцию `+=`. Поэтому гонка всё равно возникает.
- Закомментированные значения `N` (1000, 10000...) удобно показать студентам: при маленьком N гонка может не проявиться (процесс успевает закончить до конфликта), при большом проявляется стабильно.
- **Цена блокировки**: версия с `Lock` заметно медленнее, потому что процессы по очереди ждут замок. Это компромисс между корректностью и скоростью.
- `Lock` передаётся в процесс как аргумент, и все процессы используют **один и тот же** замок.

### Нюанс
Вместо отдельного замка можно использовать встроенный:
```python
with counter.get_lock():
    counter.value += 1
```

## serialization.py

### Идея
Показать, что **передача данных между процессами стоит дорого** (сериализация через pickle), и что часто лучше передавать не данные, а **способ их получить**.

### Как работает
**Вариант 1: передаём огромный список**
1. Создаётся `big_data = list(range(100_000_000))`.
2. `pool.map(process_big_list, [big_data, big_data])` отправляет список в воркеры. Для этого он **сериализуется (pickle)**, передаётся по каналу и **десериализуется** в каждом процессе. Это происходит дважды.
3. Замеряется время. Оно будет большим: сериализация и копирование занимают больше времени, чем сама сумма.

**Вариант 2: передаём только индекс**
1. В воркеры уходят маленькие числа `0, 1, 2, 3`.
2. Каждый процесс сам строит свой кусок данных (`range(start, end)`) и считает сумму.
3. Передано несколько байт вместо сотен мегабайт, поэтому это намного быстрее.

### Ключевые моменты
- Все аргументы `pool.map` и возвращаемые значения проходят через pickle. **Объём передаваемых данных напрямую влияет на скорость.**
- Принцип: *«перемещай вычисление к данным, а не данные к вычислению»*. Передавайте идентификаторы, индексы, пути к файлам, а не сами большие объекты.
- Проверка во втором варианте: сумма всех частей должна равняться `sum(range(100_000))` = 4 999 950 000.
- `sys.getsizeof(big_data)` показывает размер только **самого списка** (массив указателей, около 760 МБ). Объекты `int` внутри в эту цифру не входят, реальное потребление памяти в разы больше (несколько ГБ). Будьте осторожны с запуском на слабых машинах.

### Альтернативы для больших данных
- `multiprocessing.shared_memory` (следующий пример).
- Чтение данных из файла прямо в воркере.
- На Linux (метод `fork`) глобальные данные наследуются дочерним процессом без копирования (copy-on-write).

## shared_memory.py

### Идея
Показать, как **разделять данные между процессами без копирования и сериализации** с помощью `multiprocessing.shared_memory` и NumPy.

### Как работает
1. Создаётся обычный массив `arr` из 5 чисел `float64`.
2. `SharedMemory(create=True, size=arr.nbytes)` выделяет в ОС блок разделяемой памяти нужного размера. У блока есть уникальное **имя** (`shm.name`).
3. `np.ndarray(..., buffer=shm.buf)` создаёт массив NumPy, который смотрит **прямо в этот блок** (не копия). Данные записываются туда через `shm_arr[:] = arr[:]`.
4. «Дочернее» подключение: `SharedMemory(name=shm.name)` присоединяется к существующему блоку **по имени**. Новый `ndarray` над ним видит те же данные.
5. Очистка ресурсов.

### Ключевые моменты
- Передавать между процессами достаточно **только имя** блока (короткая строка), а не сами данные. Именно этим он решает проблему из `serialization.py`.
- Блок живёт в ОС независимо от Python-объектов. Если его не освободить, он останется в системе (утечка).
- **Правила очистки:**
  - `close()` вызывает **каждый** процесс, когда закончил работу с блоком (отключается от него);
  - `unlink()` вызывается **один раз**, обычно создателем, и удаляет блок из системы.
- Чтобы NumPy-массив правильно читал память, нужно знать `shape` и `dtype`: в блоке лежат просто байты.
- Синхронизации здесь нет. Если несколько процессов пишут в один блок, нужны `Lock` или другие механизмы (см. `atomic.py`).

### Нюансы
- В этом примере «дочерний» процесс **симулируется**: подключение выполняется в том же процессе. В реальной задаче имя блока передаётся в `Process(target=..., args=(shm.name, shape, dtype))`, и подключение делается внутри воркера.
- Если при `close()` возникает `BufferError: cannot close exported pointers exist`, перед закрытием нужно удалить массивы, ссылающиеся на буфер: `del view, shm_arr`.
