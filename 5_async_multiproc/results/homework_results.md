## Задание 3. Ответ

`asyncio.gather` по умолчанию **не отменяет** остальные задачи, если одна из них выбросила исключение — оно просто "всплывёт" после завершения всех задач (или сразу, если не передан `return_exceptions=True`, но уже запущенные задачи продолжат работать в фоне). `asyncio.TaskGroup` (Python 3.11+) реализует **структурную конкурентность**: при падении любой дочерней задачи все остальные задачи группы гарантированно отменяются, а исключения собираются в `ExceptionGroup`.

Пример: если нужно скачать несколько файлов и при сбое одного из них немедленно прекратить остальные закачки (чтобы не тратить трафик впустую), предпочтительнее `TaskGroup`.

## Задание 4. Ответ

Результат **не всегда** будет равен `400000`, хотя интуитивно кажется, что GIL должен это гарантировать. GIL защищает атомарность отдельных байткод-инструкций, но `counter += 1` — это не одна атомарная операция (чтение → инкремент → запись), и GIL может переключить поток между этими шагами. На практике в CPython из-за особенностей переключения потоков ошибка встречается редко, но теоретически возможна — корректное решение требует `threading.Lock`.

## Задание 5. Ответ

| Конструкция | Что делает | Когда использовать |
|---|---|---|
| `asyncio.Semaphore(n)` | Ограничивает число одновременно выполняющихся корутин значением `n` | Когда нужно ограничить конкурентность (например, число одновременных запросов к API с rate limit) |
| `multiprocessing.Pool` | Создаёт пул процессов-воркеров и распределяет задачи между ними | Для CPU-bound задач, которые можно разбить на независимые части |
| `asyncio.to_thread(func)` | Запускает синхронную блокирующую функцию в отдельном потоке, не блокируя event loop | Когда нужно вызвать блокирующий синхронный код (legacy-библиотеку) внутри асинхронного приложения |
| `shared_memory.SharedMemory` | Организует разделяемую память между процессами без сериализации через pickle | Для больших NumPy-массивов, когда копирование через pickle слишком дорого |

## Задание 8. Ответ

Задача комбинированная: сначала I/O-bound этап (скачивание 500 URL), затем CPU-bound этап (парсинг и агрегация).

Рекомендуемый подход — двухэтапный конвейер:
1. **Этап скачивания:** использовать `asyncio` + `aiohttp` с `Semaphore` для ограничения числа одновременных подключений (чтобы не перегружать сеть/сервер). Это эффективно использует I/O-ожидание без накладных расходов на потоки ОС.
2. **Этап обработки:** передать скачанные документы в `ProcessPoolExecutor` (или `multiprocessing.Pool`), чтобы задействовать несколько ядер CPU для тяжёлого парсинга — GIL не позволит это сделать эффективно ни через `asyncio`, ни через `threading`.

Такое разделение соответствует таблице выбора инструмента из главы: I/O → asyncio, CPU → multiprocessing.

## Задание 10. Ответ

```python
class AsyncConnection:
    async def __aenter__(self):
        print("Подключение установлено")
        return self

    async def query(self, sql):
        print(f"Выполняется запрос: {sql}")

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        print("Соединение закрыто")
        return False
```

Если `__aexit__` вернёт `True`, это означает, что метод "поглотил" исключение — оно будет **подавлено** и не будет распространяться дальше за пределы блока `async with`, что обычно является нежелательным побочным эффектом и может скрыть реальную ошибку в программе.
