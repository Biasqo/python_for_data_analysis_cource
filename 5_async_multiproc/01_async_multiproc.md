# Глава 5 - Продвинутый Python: AsyncIO и Многопроцессорность

## Часть 1. Модели конкурентности

### 1.1 Конкурентность vs Параллелизм

**_Конкурентность_**

*Конурентность* можно изобразить схематично на примере двух очередей которые стоят на **одну** кассу:

```text
    ┌─────┐      ┌─────┐
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    └──┬──┘      └──┬──┘
       │            │
       └──────┬─────┘
              ▼
       ╔══════════╗
       ║   КАССА  ║
       ╚══════════╝
```

Покупатели стоят в двух очередях одновременно.\
Касса одна, поэтому в каждый момент времени она обслуживает только одного человека.\
Касса переключается между очередями: например, берет одного из очереди 1, потом одного из очереди 2, потом снова из очереди 1 и т.д.

То же самое происходит на ядре, который принимает входящие на него задачи

**_Параллелизм_**

*Параллелизм* можно изобразить схематично на примере двух очередей которые стоят на **две** кассы:

```text
    ┌─────┐      ┌─────┐
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    │ ███ │      │ ███ │
    └──┬──┘      └──┬──┘
       │            │
       ▼            ▼
   ╔═══════╗    ╔═══════╗
   ║ КАССА ║    ║ КАССА ║
   ║   1   ║    ║   2   ║
   ╚═══╤═══╝    ╚═══╤═══╝
```

| Конкурентность | Параллелизм |
|---|---|
| Свойство *структуры* программы | Свойство *исполнения* программы |
| Задача разбита на части, которые могут чередоваться | Части выполняются физически одновременно |
| Возможна на одном ядре | Требует нескольких ядер |
| Пример: `asyncio` на одном потоке | Пример: `multiprocessing` на 4 ядрах |

Конкурентность - необходимое, но не достаточное условие параллелизма. Программа может быть высококонкурентной (много точек `await`) и при этом полностью непараллельной - один поток, одно ядро.

### 1.2 Модель памяти CPython и GIL

| Термин | Определение |
|---|---|
| **GIL** | Global Interpreter Lock - mutex интерпретатора, гарантирующий, что байткод в любой момент исполняет только один поток |
| **Reference counting** | Механизм подсчёта ссылок CPython, ради атомарности которого и введён GIL |

GIL - следствие выбора **non-atomic reference counting**: каждый объект хранит счётчик ссылок, который нужно инкрементировать/декрементировать при каждом присваивании. Без глобальной блокировки эти операции требовали бы atomic-инструкций или блокировки на каждый объект, что замедлило бы подавляющее большинство однопоточных программ.

```
                CPU-ограниченная задача   I/O-ограниченная задача
Threading       ❌ GIL сериализует        ✅ Освобождается на syscall
Asyncio         ❌ Один поток              ✅ Кооперативный event loop
Multiprocessing ✅ Отдельный GIL/процесс   ⚠️ IPC/сериализация
```

_Лирическое отсупление_

GIL не позволяет CPU-задачам выполняться параллельно в потоках, даже на многоядерных системах - по сути, многопоточная программа становится однопоточной. Для высоконагруженных приложений это критично, так как не дает эффективно использовать все ядра процессора для тяжелых вычислений.
Попытки обойти это через multiprocessing создают дополнительные накладные расходы по памяти и управлению процессами.
Обходным путем является написание некоторых функций на С для работы "из под капота" Python, а также использование библиотек написанных на С или других более производительных языках программирования (Rust, C).\
`multiprocessing` потребляет много памяти, потому что каждый процесс - это независимый интерпретатор CPython со своей копией кода, глобальных переменных, импортированных модулей и данных. На Unix используется fork (copy-on-write), на Windows - spawn (полный перезапуск). В результате процесс, занимающий 500 МБ, при создании 4 процессов может съесть более 2 ГБ ОЗУ, что критично для систем с ограниченными ресурсами.

Все это делает python не очень востребованным языком для инфраструктурной разработки и разработки highload приложений.

**Формула для оценки threading на I/O-задачах:**

```
T_total ≈ T_compute + T_io / min(N_threads, degree_of_io_overlap)
```

Вычислительная часть не делится между потоками - GIL сериализует байткод-исполнение. Выигрывает только I/O-часть, потому что блокирующие syscalls (`read()`, `recv()`) освобождают GIL на время ожидания ядра.

### 1.3 Будущее GIL: PEP 703

_Лирическое отступление_:
Начиная с CPython 3.13 существует experimental **free-threaded build** (PEP 703), убирающий GIL за счёт biased reference counting и per-object locks. Это не отменяет модель "I/O vs CPU" из этой главы, но означает, что многопоточный CPU-parallelism в Python перестаёт быть теоретически невозможным.

| Задача | Нужен ли multiprocessing без GIL? | Почему |
|---|---|---|
| CPU-bound вычисления | Не обязательно | Free-threaded build даёт истинный параллелизм потоков |
| Изоляция от крашей | Да | Процессы всё ещё независимы по памяти |
| Non-Uniform Memory Access | Да | Cache contention остаётся даже без GIL |

## Часть 3. AsyncIO

### 3.1 Coroutine, Task, Future

| Сущность | Что это |
|---|---|
| **Coroutine** | Объект, созданный вызовом `async def` функции - ещё не запущен |
| **Task** | Обёртка над корутиной, зарегистрированная в event loop для исполнения |
| **Future** | Низкоуровневый объект-placeholder для результата, который появится позже |

Событийный цикл (создаётся `asyncio.run`) - это, по сути, `while True` вокруг системного вызова `select`/`epoll`/`kqueue`: он опрашивает файловые дескрипторы на готовность и возобновляет соответствующую корутину с места последнего `await`.

*Event loop* - это ядро любого asyncio-приложения. 
*Event loop* - бесконечный цикл, который управляет выполнением асинхронного кода в одном потоке.

Он выполняет три основные задачи:
1. Запускает и управляет корутинами и задачами (`run_forever`, `run_until_complete`, `create_task`).
2. Обрабатывает операции ввода-вывода (сеть, файлы, подпроцессы) через неблокирующие системные вызовы (`create_connection`, `create_server`, `add_reader`).
3. Планирует отложенные вызовы (`call_soon`, `call_later`, `call_at`).

Блокировка Event loop:

1. Синхронный сон: `time.sleep()`
2. CPU-интенсивные вычисления: циклы, рекурсия, математика
3. Синхронный ввод-вывод (I/O): `open(), read(), write()`
4. Синхронные сетевые запросы: `requests.get()`
5. Работа с БД через синхронные драйверы: `psycopg2, pymongo`
6. Любой синхронный код без await внутри

Нет блокировки Event loop:

1. await asyncio.sleep()
2. await aiohttp.get()
3. await aiofiles.open()
4. await aiomysql.connect()
5. await asyncio.to_thread(blocking_func)
6. Любая операция с await внутри

_Формула расчета времени работы_
`T = ceil(N / S) * D`, где N - общее количество задач, S - количество разрешений семафора, D - время выполнения одной задачи (секунды)

### 3.4 `gather` vs `as_completed` vs `TaskGroup`

| Инструмент | Порядок результатов | Поведение при исключении |
|---|---|---|
| `asyncio.gather` | Сохраняется исходный порядок | По умолчанию не отменяет остальные задачи |
| `asyncio.as_completed` | По мере готовности | Каждая задача обрабатывается независимо |
| `asyncio.TaskGroup` (3.11+) | Не гарантирован | Гарантированно отменяет все дочерние задачи |

### 3.5 Структурная конкурентность

Если одна из задач в `TaskGroup` падает с исключением, **все остальные задачи группы
гарантированно отменяются** - это и есть структурная конкурентность.

Идея (по аналогии со структурным программированием vs `goto`): время жизни любой конкурентной задачи должно быть строго вложено в область видимости, которая её создала.

Без `TaskGroup` задача, созданная через `create_task` без сохранённой ссылки, может быть собрана сборщиком мусора до завершения - источник трудновоспроизводимых багов в продакшене.

### 3.6 Асинхронные контекстные менеджеры

```python
АСИНХРОННЫЕ КОНТЕКСТНЫЕ МЕНЕДЖЕРЫ (async with)

Обычный with не умеет работать с асинхронным кодом. 
Если внутри __enter__ или __exit__ нужно сделать await (подключиться к БД, открыть файл, захватить блокировку), обычный with не сработает. 
async with решает эту проблему.

Действия:

1. __aenter__() - выполняется при входе в блок
   - Асинхронно подключается к БД
   - Открывает сетевое соединение
   - Захватывает асинхронную блокировку
   - Возвращает объект для работы

2. Тело блока async with - выполняются операции
   - Например, запросы к БД через await conn.query()

3. __aexit__() - выполняется ПРИ ВЫХОДЕ из блока
   - Асинхронно закрывает соединение
   - Освобождает ресурсы
   - Коммитит транзакцию
   - Вызывается даже при возникновении исключения

Обычный with:
- Синхронный __enter__ и __exit__
- Не может использовать await
- Блокирует event loop на время входа/выхода

async with:
- Асинхронный __aenter__ и __aexit__
- Может использовать await
- Не блокирует event loop

Примеры использования:

- Нужно асинхронно открыть/закрыть ресурс
- Есть I/O-операции при входе/выходе
- Нужно гарантированно освободить ресурс
- Работа с БД, сетью, файлами

async with гарантирует, что ресурс будет освобожден даже при исключении внутри блока. 
Это основная причина использовать контекстные менеджеры вместо ручного управления ресурсами.
```

### 3.7 Асинхронные генераторы

```python
Асинхронный генератор (async for)

Используется, когда каждый следующий элемент нужно асинхронно (ждем данные из сети, БД, файла).

- Обычный for: все данные уже готовы в памяти
- async for: каждый элемент приходит через await

Варианты использования:
- Потоковые данные с API
- Пагинация (страницы подгружаются по мере чтения)
- WebSocket сообщения
- Чтение больших файлов по частям

Действия:
1. Запрашиваем следующий элемент (await)
2. Ждем, пока он придет
3. Обрабатываем
4. Переходим к следующему (если есть)

async for не блокирует event loop между элементами.
```

## Часть 4. Многопроцессорность

### 4.1 Базовая модель

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                          Main                                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  from multiprocessing import Process                                    │
│                                                                         │
│  def worker(): ...                                                      │
│                                                                         │
│  if __name__ == "__main__":                                             │
│      p = Process(target=worker)  ◄───── 1. Иниациализация               │
│      p.start()  ◄──────────────────── 2. Старт                          │
│      p.join()  ◄───────────────────── 3. Ожидание завершения            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
                                         
                                         
  ┌─────────────────────────────────────────────────────────────────────┐
  │                   ДОЧЕРНИЙ ПРОЦЕСС                                  │
  ├─────────────────────────────────────────────────────────────────────┤
  │                                                                     │
  │  p.start() ──────────────────────────┐                              │
  │                                      │                              │
  │  1. Запускается новый интерпретатор  │                              │
  │  2. Импортирует модуль               │                              │
  │  3. Выполняет target=worker()        │                              │
  │  4. Завершается                      │                              │
  │                                      │                              │
  │  p.join() ◄─────────────────────────────────────────────────────────┘
  │  (ждет, пока дочерний не завершится)                                │
  │                                                                     │
  └─────────────────────────────────────────────────────────────────────┘

Обмен данными:

┌──────────────┐     Queue/Pipe     ┌──────────────┐
│   ГЛАВНЫЙ    │ ◄────────────────► │   ДОЧЕРНИЙ   │
│   ПРОЦЕСС    │     (IPC)          │   ПРОЦЕСС    │
└──────────────┘                    └──────────────┘
     │                                      │
     │     ┌──────────────────────┐         │
     └─────│   Общая память       │─────────┘
           │   (Manager)          │
           └──────────────────────┘
```

**Зачем нужен `if __name__ == "__main__"`:** на Windows и macOS новые процессы создаются через `spawn` - повторный импорт модуля в дочернем процессе. 
Без защиты каждый дочерний процесс заново исполняет код верхнего уровня модуля, порождая рекурсивное создание процессов. 
На Linux (`fork`) проблема не проявляется так остро, но защита обязательна для кросс-платформенного кода.

### 4.2 `Pool` и `ProcessPoolExecutor`

Модуль `multiprocessing` предоставляет низкоуровневый API для работы с процессами, а `concurrent.futures` - более современный и высокоуровневый интерфейс. 
Оба решают одну задачу: обход GIL (Global Interpreter Lock) для CPU-интенсивных задач через запуск нескольких процессов-воркеров.

#### Сравнение `Pool` и `ProcessPoolExecutor`

`Pool` - классический инструмент для параллельной обработки данных в Python. Он создает пул воркеров и распределяет между ними задачи.

`ProcessPoolExecutor` - более современный и единообразный API, входящий в стандартную библиотеку начиная с Python 3.2. 
Реализует тот же интерфейс, что и ThreadPoolExecutor, что позволяет легко переключаться между потоками и процессами.

### 4.3 Издержки сериализации

Данные между процессами передаются через **pickle**. Из этого следует:

| Проблема | Последствие |
|---|---|
| Каждый аргумент и результат сериализуется | Для больших объектов (DataFrame на сотни МБ) это может занимать больше времени, чем сами вычисления |
| Не всё сериализуется | Файловые дескрипторы, сокеты, лямбды, некоторые соединения с БД - падают с ошибкой |

```python
# ❌ Дорого - весь df копируется в каждый процесс через pickle
with Pool(4) as pool:
    pool.map(lambda chunk: chunk.sum(), [df, df, df, df])

# ✅ Лучше - каждый процесс сам читает свой файл с диска
with Pool(4) as pool:
    pool.map(process_file, file_paths)
```

### 4.4 Обход сериализации: `shared_memory`

Для больших NumPy-массивов можно обойти pickle-копирование через разделяемую память:

`shared_memory` позволяет организовать разделяемую память между процессами без сериализации: родительский процесс создает именованный блок памяти и размещает в нем массив, а дочерние процессы подключаются к этому же блоку по имени, получая прямой доступ к данным через numpy.ndarray без копирования. 

Это эффективно для больших массивов, но требует ручного управления временем жизни (удаление через shm.close() и shm.unlink()) и поддерживается только для массивов с непрерывным хранением в памяти.
Разделяемая память работает быстрее и экономит память, но усложняет синхронизацию и не подходит для объектов, отличных от numpy.ndarray.

_Лирическое отступление_:
Это меняет модель безопасности - процессы больше не изолированы полностью, гонки данных снова становятся возможны, как в threading, поэтому нужна явная синхронизация (`multiprocessing.Lock`).
Можно отметить что это очень похоже на написание кода на С.

## Часть 5. Выбор инструмента

```
Задача ограничена I/O? (сеть, диск, API)
├── Да → asyncio (или threading для legacy блокирующих библиотек)
└── Нет → Ограничена CPU? (вычисления, парсинг, ML-инференс)
           ├── Да → multiprocessing.Pool / ProcessPoolExecutor
           │         ├── Данные огромны для pickle? → shared_memory или векторизация
           │         └── Задача < ~100 мс? → накладные расходы IPC не оправданы
           └── Нет → последовательный код - оптимально
```

### 5.2 Примеры для анализа данных

| Задача | Инструмент | Обоснование |
|---|---|---|
| Скачать 100 CSV с S3 | asyncio / aiohttp | I/O-bound |
| Пакетные запросы к внешнему API | asyncio + Semaphore | I/O-bound, rate limit |
| Предобработка 50 CSV параллельно | multiprocessing.Pool | CPU-bound |
| Grid search гиперпараметров | ProcessPoolExecutor | CPU-bound, независимые задачи |
| Нормализация DataFrame 10M строк | Векторизация NumPy | Избегаем накладных расходов вообще |
| Стрим событий в реальном времени | asyncio + async generator | Конкурентный I/O |
| Общий большой NumPy-массив между воркерами | shared_memory | Избегаем pickle-копирования |

### 5.3 Итоговая таблица

| Критерий | Threading | AsyncIO | Multiprocessing |
|---|---|---|---|
| Обходит GIL | Нет | Нет (не нужно) | Да |
| Подходит для I/O | Да | Да (эффективнее) | Избыточно |
| Подходит для CPU | Нет | Нет | Да |
| Издержки на единицу конкурентности | Память потока ОС (~8 МБ) | Минимальны (объект Task) | IPC/сериализация |
| Риск гонок данных | Да (нужен Lock) | Нет (один поток) | Только при shared_memory |
