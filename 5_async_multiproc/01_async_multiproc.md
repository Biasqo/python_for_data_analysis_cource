## 1. Введение (5 мин)

Открывающий вопрос классу: *«Кто из вас писал код, который просто ждёт — ответа от API, чтения файла с диска, ответа базы данных? А что в это время делает ваш процессор?»*

Ответ: почти ничего. Он простаивает. Конкурентность и параллелизм — это способы не тратить это время впустую.

**Почему это важно именно для аналитика данных, а не только для backend-разработчика:**
- Каждый день вы ждёте ответов от API (Bloomberg, S3, внутренние сервисы) — это чистые потери времени без async.
- Обработка десятков/сотен файлов — либо ждать по очереди, либо запускать параллельно.
- Плохое понимание этой темы = скрипты, которые работают часами, хотя могли бы работать минуты.

## 2. Конкурентность vs Параллелизм, и GIL (15 мин)

| Термин | Определение |
|---|---|
| **Конкурентность** | Выполнение нескольких задач путём чередования прогресса (одно ядро) |
| **Параллелизм** | Фактическое одновременное выполнение нескольких задач (несколько ядер) |
| **GIL** | Global Interpreter Lock — в один момент времени только один поток выполняет байткод Python |

Важно подчеркнуть: **конкурентность ≠ параллелизм**. Конкурентность — это про *структуру* задачи (можно ли её разбить на переключаемые куски), параллелизм — про *физическое* одновременное исполнение на разных ядрах.

```
                CPU-ограниченная задача   I/O-ограниченная задача
                (вычисления)              (сеть/диск)
Threading       ❌ GIL блокирует          ✅ Потоки освобождают GIL во время I/O
Asyncio         ❌ Однопоточный           ✅ Кооперативная многозадачность
Multiprocessing ✅ Обходит GIL            ⚠️  Накладные расходы на сериализацию
```

**Аналогия для доски:** Представьте GIL как единственную будку на шоссе (turnstile). Даже если у вас несколько машин (потоков), через неё проезжает только одна за раз. При длительном ожидании (I/O) машина уступает дорогу другим — GIL освобождается. Но для чистых вычислений (быстрой езды без остановок) нужны параллельные шоссе — то есть отдельные процессы, у каждого из которых свой GIL.

### Почему GIL вообще существует?

Короткое отступление, полезное для вопросов из зала: GIL упрощает управление памятью в CPython (счётчики ссылок не требуют блокировок на каждую операцию), но ценой того, что потоки Python не могут по-настоящему параллельно выполнять байткод. Это не «баг», а осознанный компромисс дизайна интерпретатора CPython.

### Почему это важно для аналитиков данных?
- Пакетные API-запросы (получение макроданных) → **asyncio**.
- Параллельная предобработка больших CSV-файлов → **multiprocessing**.
- `.apply()` в Pandas на больших DataFrame → **multiprocessing** (или **векторизация**!).

**Проверочный вопрос классу:** «Если я использую threading для расчёта чисел Фибоначчи на 4 потоках, ускорится ли код в 4 раза?» — Нет, из-за GIL. Ускорение будет практически отсутствовать или код может даже замедлиться из-за накладных расходов на переключение потоков.

## 3. Threading — краткий обзор для контраста (10 мин)

Прежде чем перейти к asyncio, полезно показать threading, чтобы студенты видели разницу в подходах к I/O-задачам.

```python
import threading
import time

def download(name: str, delay: float) -> None:
    print(f"Начало загрузки {name}")
    time.sleep(delay)  # имитация сетевого запроса
    print(f"Загрузка {name} завершена")

threads = [
    threading.Thread(target=download, args=(f"файл_{i}", 2))
    for i in range(5)
]

start = time.time()
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"Всего: {time.time() - start:.1f} сек")  # ~2 сек, а не 10
```

**Ключевая мысль:** потоки работают для I/O, потому что `time.sleep()` (и реальные сетевые вызовы) освобождают GIL. Но у потоков есть накладные расходы (память на каждый поток, переключение контекста ОС) и риски гонок данных (race conditions), требующие блокировок (`Lock`).

**Переход к asyncio:** asyncio решает ту же задачу (много I/O-ожиданий), но без накладных расходов на потоки ОС — всё происходит в одном потоке с явным переключением между задачами.

## 4. AsyncIO: концепция и синтаксис (20 мин)

### 4.1 Идея кооперативной многозадачности

В asyncio задача сама говорит: «Я сейчас буду ждать — можешь пока заняться другими задачами». Это происходит через ключевое слово `await`. В отличие от потоков, где ОС может прервать поток в любой момент, здесь переключение происходит только в явных точках `await` — отсюда «кооперативная».

### 4.2 Базовый синтаксис

```python
import asyncio
import time

async def download(name: str, delay: float) -> None:
    print(f"Начало загрузки {name}")
    await asyncio.sleep(delay)  # НЕ time.sleep()! — не блокирует событийный цикл
    print(f"Загрузка {name} завершена")

async def main() -> None:
    start = time.time()
    # Запускаем все задачи "одновременно"
    await asyncio.gather(
        download("файл_1", 2),
        download("файл_2", 2),
        download("файл_3", 2),
    )
    print(f"Всего: {time.time() - start:.1f} сек")  # ~2 сек, а не 6

asyncio.run(main())
```

**Частая ошибка новичков — обязательно показать на доске:**

```python
# НЕПРАВИЛЬНО — время.sleep() блокирует весь событийный цикл
async def bad(delay):
    time.sleep(delay)   # ❌ Блокирует ВСЁ, а не только эту задачу

# ПРАВИЛЬНО
async def good(delay):
    await asyncio.sleep(delay)   # ✅ Освобождает цикл событий другим задачам
```

Это правило распространяется на любые синхронные блокирующие вызовы: `requests.get()` вместо `aiohttp`, синхронное чтение файлов и т.д. — всё это «замораживает» событийный цикл целиком.

### 4.3 Реальный пример: пакетные API-запросы

```python
import asyncio
import aiohttp

async def fetch_price(session: aiohttp.ClientSession, ticker: str) -> dict:
    url = f"https://api.example.com/price/{ticker}"
    async with session.get(url) as response:
        return await response.json()

async def fetch_all_prices(tickers: list[str]) -> list[dict]:
    async with aiohttp.ClientSession() as session:
        tasks = [fetch_price(session, t) for t in tickers]
        return await asyncio.gather(*tasks)

tickers = ["AAPL", "MSFT", "GOOG", "AMZN", "TSLA"]
results = asyncio.run(fetch_all_prices(tickers))
```

**Сравнение производительности (для обсуждения в классе):**
Если каждый запрос занимает 300 мс, а тикеров 100:
- Последовательно (`requests` в цикле): ~30 секунд
- Параллельно (`aiohttp` + `asyncio.gather`): ~0.3–1 секунда (ограничено сетью, не суммой задержек)

### 4.4 `asyncio.gather` vs `asyncio.as_completed`

```python
# gather — ждём все сразу, результаты в исходном порядке
results = await asyncio.gather(task1, task2, task3)

# as_completed — обрабатываем по мере готовности (полезно для прогресс-баров)
for coro in asyncio.as_completed([task1, task2, task3]):
    result = await coro
    print(f"Готово: {result}")
```

### 4.5 Ограничение конкурентности: `asyncio.Semaphore`

Важный практический момент: если у вас 1000 тикеров, а API разрешает не более 10 одновременных запросов — нельзя просто запустить все через `gather`.

```python
async def fetch_with_limit(session, ticker, semaphore):
    async with semaphore:
        return await fetch_price(session, ticker)

async def fetch_all_limited(tickers: list[str]) -> list[dict]:
    semaphore = asyncio.Semaphore(10)  # максимум 10 одновременно
    async with aiohttp.ClientSession() as session:
        tasks = [fetch_with_limit(session, t, semaphore) for t in tickers]
        return await asyncio.gather(*tasks)
```

**Обсудить с классом:** зачем это нужно? (Чтобы не получить бан от API за превышение rate limit, и чтобы не открывать тысячи одновременных соединений.)

## 5. Асинхронные контекстные менеджеры и генераторы (10 мин)

### 5.1 Асинхронные контекстные менеджеры — для ресурсов, требующих завершения

Обычный `with` не умеет ждать асинхронно при входе/выходе. Для этого существует `async with`.

```python
class AsyncDatabaseConnection:
    async def __aenter__(self):
        print("Открываем соединение...")
        await asyncio.sleep(0.1)  # имитация асинхронного подключения
        return self

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        print("Закрываем соединение...")
        await asyncio.sleep(0.1)  # имитация асинхронного закрытия

    async def query(self, sql: str) -> list:
        await asyncio.sleep(0.2)
        return [{"result": "данные"}]

async def main():
    async with AsyncDatabaseConnection() as conn:
        data = await conn.query("SELECT * FROM prices")
        print(data)
    # соединение автоматически и асинхронно закрыто

asyncio.run(main())
```

Это ровно то, что происходит «под капотом» в `aiohttp.ClientSession()` из предыдущего примера — сессия асинхронно открывается и закрывается.

### 5.2 Асинхронные генераторы — для потоковых данных

Полезно, когда данные приходят порциями (например, построчное чтение большого файла или стрим событий).

```python
async def stream_prices(ticker: str):
    for i in range(5):
        await asyncio.sleep(0.5)  # имитация поступления новой цены
        yield {"ticker": ticker, "price": 100 + i}

async def main():
    async for price in stream_prices("AAPL"):
        print(price)

asyncio.run(main())
```

**Ключевая мысль:** `async for` нужен именно потому, что получение *каждого* следующего элемента может требовать ожидания (I/O), в отличие от обычного генератора, где элементы уже готовы.

## 6. Многопроцессорность (15 мин)

### 6.1 Зачем — обход GIL для CPU-задач

```python
from multiprocessing import Process

def worker(n: int) -> None:
    result = sum(i**2 for i in range(n))
    print(f"Сумма квадратов до {n}: {result}")

if __name__ == "__main__":  # ОБЯЗАТЕЛЬНО — требуется в Windows/macOS
    p = Process(target=worker, args=(1_000_000,))
    p.start()
    p.join()   # ждать завершения
```

**Зачем нужен `if __name__ == "__main__"`?**
В Windows новые процессы создаются путём импорта модуля — без этой защиты возникает бесконечная рекурсия, так как каждый дочерний процесс порождает новые дочерние. На Linux/macOS (fork) проблема менее острая, но защита всё равно является хорошей практикой и обязательна для кросс-платформенного кода.

### 6.2 Практичный инструмент: `multiprocessing.Pool`

На практике почти никогда не создают `Process` вручную — используют `Pool`, который сам распределяет задачи по воркерам.

```python
from multiprocessing import Pool
import pandas as pd

def process_file(filepath: str) -> pd.DataFrame:
    df = pd.read_csv(filepath)
    df["normalized"] = (df["value"] - df["value"].mean()) / df["value"].std()
    return df

if __name__ == "__main__":
    files = [f"data_{i}.csv" for i in range(50)]

    with Pool(processes=4) as pool:  # обычно = число ядер процессора
        results = pool.map(process_file, files)

    final_df = pd.concat(results, ignore_index=True)
```

**Обсудить с классом:** сколько ставить `processes`? Обычно — количество физических ядер (`os.cpu_count()`), но не всегда больше = быстрее из-за накладных расходов на межпроцессное взаимодействие.

### 6.3 Накладные расходы на сериализацию (важная ловушка!)

Данные между процессами передаются через **pickle** (сериализация). Это значит:
- Большие DataFrame'ы копируются в каждый процесс — дорого по памяти и времени.
- Некоторые объекты нельзя сериализовать вообще (например, открытые файловые дескрипторы, лямбда-функции, соединения с БД).

```python
# ПРОБЛЕМА: если filepath указывает на файл в 5 ГБ,
# каждый процесс должен сам загрузить и обработать данные —
# это нормально, если это ЧТЕНИЕ с диска в каждом процессе,
# но плохо, если вы пытаетесь передать уже загруженный DataFrame:

# ❌ Дорого — весь df копируется в каждый процесс через pickle
with Pool(4) as pool:
    pool.map(lambda chunk: chunk.sum(), [df, df, df, df])

# ✅ Лучше — каждый процесс сам читает свой файл с диска
with Pool(4) as pool:
    pool.map(process_file, file_paths)
```

### 6.4 `ProcessPoolExecutor` — альтернативный, более современный API

```python
from concurrent.futures import ProcessPoolExecutor

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(process_file, files))
```

Стоит упомянуть: `concurrent.futures` даёт единый интерфейс (`ThreadPoolExecutor` / `ProcessPoolExecutor`) с одинаковым API — удобно, если нужно легко переключаться между потоками и процессами при экспериментах с производительностью.

## 7. Дерево решений (10 мин)

**Вывести на экран и разобрать с классом:**

```
Задача ограничена I/O? (сеть, диск, API-запросы)
├── Да → asyncio (или threading для блокирующих библиотек)
└── Нет → Ограничена CPU? (вычисления, парсинг, ML)
           ├── Да → multiprocessing.Pool
           │         ├── Но: данные огромны для сериализации? → рассмотрите векторизацию (NumPy)
           │         └── Или: каждая задача < 100 мс? → накладные расходы не оправданы
           └── Нет → последовательный код вполне подойдёт
```

**Конкретные примеры для анализа данных:**

| Задача | Правильный инструмент | Почему |
|---|---|---|
| Скачать 100 CSV с S3 | asyncio / aiohttp | Ограничена I/O |
| Пакетные API-запросы к Bloomberg | asyncio | Ограничена I/O |
| Параллельная предобработка 50 CSV-файлов | multiprocessing.Pool | Ограничена CPU |
| Обучение ML-моделей с разными гиперпараметрами | multiprocessing.Pool | Ограничена CPU |
| Нормализация DataFrame из 10M строк | Векторизация NumPy | Полностью избегаем накладных расходов |
| Потоковая обработка событий в реальном времени | asyncio | Конкурентный I/O |
| Чтение и парсинг лог-файла построчно, где строки независимы | multiprocessing.Pool | Ограничена CPU (парсинг) |
| Опрос 5 разных внутренних микросервисов | asyncio | Ограничена I/O, много ожидания |

### Мини-кейс для разбора в классе (5 мин обсуждения)

*«У вас есть 200 000 строк с адресами клиентов. Для каждой строки нужно: (1) отправить запрос в geocoding API, чтобы получить координаты, и (2) применить сложную математическую формулу очистки координат. Какой подход выбрать?»*

Ожидаемый ответ от студентов: это гибридная задача — шаг (1) I/O-ограничен (asyncio), шаг (2) CPU-ограничен (multiprocessing). Правильная архитектура: сначала асинхронно собрать все ответы API (с ограничением по `Semaphore`, чтобы не превысить rate limit), затем передать результаты в `multiprocessing.Pool` для тяжёлых вычислений. Смешивать asyncio и multiprocessing в одном процессе напрямую сложно — но можно комбинировать: сначала одна стадия, потом другая.
